# ADR-004: Qt qrc 资源打包进静态库时的初始化陷阱

- 状态: 已采纳(实测踩过并修复)
- 日期: 2026-07-18

## 背景

`ur_gfx` 把烘焙好的着色器(`.qsb`)通过 Qt 资源系统(`.qrc`)嵌入二进制,
避免运行时依赖外部文件路径。`ur_gfx` 本身是静态库,被 `ur_gfx_tests`
可执行文件链接。

实测中这个组合直接复现了一个经典的 Qt + 静态库问题:qrc 生成的资源
初始化是一个全局构造函数,当它所在的编译单元被打包进静态库、且没有
任何其他符号从这个编译单元被直接引用时,链接器会把整个编译单元当成
死代码裁掉 —— 资源注册代码根本没有执行,导致运行时 `:/prefix/file`
查找全部失败(表现为"文件不存在"而不是明显的链接错误,容易被误判成
路径写错)。

进一步实测发现,修复过程本身有两层坑:
1. `Q_INIT_RESOURCE(shaders)` 宏生成的符号名字修饰要求调用点在**真正的
   全局命名空间**,连 C++ 匿名命名空间都不行(匿名命名空间仍然会改变
   符号修饰)。
2. 必须在消费方(这里是 `VulkanRenderDevice` 构造函数)显式调用这个
   初始化函数,强制链接器保留资源翻译单元。

## 决策

`ur_gfx/src/vulkan_render_device.cpp` 里保留一个不在任何 namespace
块内的 `static void initShaderResourcesGlobal()` 函数,内部调用
`Q_INIT_RESOURCE(shaders)`,由 `VulkanRenderDevice` 构造函数显式调用。

团队规范: 任何模块只要把 Qt 资源(qrc)打包进静态库,都必须遵循这个
模式 —— 不能假设"链进最终可执行文件就会自动生效"。

## 后果

- 这类问题在集成测试阶段才会暴露(单独编译库不会报错,只有运行时资源
  查找失败才能发现),CI 的单元测试覆盖率必须包含"资源确实能被加载"
  这一断言,不能只测试逻辑不测试资源系统本身。
- 未来任何新模块(比如 `ur_text` 以后要嵌入字体文件、`ur_widgets`
  要嵌入图标)如果走 Qt 资源系统,都要在模块自己的测试里加一条
  "资源能正确加载"的用例,而不是假设这个机制默认可靠。
